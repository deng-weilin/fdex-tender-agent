# 学员任务说明写法

任务书要让新学员在不先背接口缩写的情况下，说清楚要替谁解决什么问题，以及交出什么才算完成。技术约定保留，但放在业务说明后面。

## 固定阅读顺序

1. 你在帮谁解决什么问题：具体使用者、收到什么、哪里会出错，以及这次要补的功能。
2. 我们提供哪些材料：真实存在的仓库位置、每份材料作用、故意缺件，以及还没准备的资料。
3. 你具体要做什么：按动作列步骤，说明基座已有能力和本次新增，不把整个模块路线图当一个任务。
4. 做完后交什么：明确实际文件和中文说明，给一个与本任务对应的交付效果例子，列不做的内容和接手者。
5. 怎么判断完成：本任务正常、需核对、异常和变更场景；实际原件与输出的验证，不只写AC编号。
6. 技术附录：术语释义、输出JSON名称、已有接口、测试命令、PR证据和协作规则。

## 必须逐项判断

M03直接从文件列表开始，不能要求它虚构“实际生成的上游JSON”；M12可先独立计算，不被强制等待全本装配。只有M13等实际制作任务要生成DOCX；M14检查已有DOCX，其他任务不附带泛化的Word交付要求。前序数据的联调要与真实读取关系对应。

材料目录的GitHub地址使用tree，文件地址使用blob；正文中用中文解释正常、待核对、异常和变更用例，程序编号与字段放到技术附录。资料位置必须可访问，不用不确定的“去问老师要附件”代替已经提供的文件。

开放任务要列出已经存在的材料；未开放任务明确待维护者准备的输入和预期，不让学员认领后才发现要自行出题或补客户原件。示意例子不能伪装成已提供的测试文件。

业务建议、来源事实、人工确认和程序完成状态分开。写清“读到证书字段不等于证书真伪核验”“计算正确不等于批准报价”“生成包不等于递交成功”“局部检查不等于全本验收”等本任务边界。

## 维护方式

19项课程任务的逐项内容在 configs/task-briefs.json，任务身份与状态计划仍在 configs/tasks.json。`python tools/task_descriptions.py --write-docs`只根据这些作者内容渲染任务书，不生成业务结果或测试答案。原始需求保持不改。

GitHub同步先做全量快照，再仅更新标题和正文；保留隐藏任务编号、标签、负责人、状态和评论。后续说明更新只替换受管理的正文区域，外部备注保留。不要关闭Issue来表示文字改写完成，也不把改写当独立工程批准。
